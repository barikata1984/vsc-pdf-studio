# 2026-09-09 PDF 表示性能改善と配布方針

## Topic
PDF 表示性能の改善、VSIX の作成、upstream への反映方法を検討した記録

## Summary
全ページ描画による開始時負荷と画面外資源の蓄積を避けるため、表示範囲を中心とする描画へ変更した。
縮小画像と文字索引が画面操作と競合するため、付随処理は必要時に実行する方式へ変更した。
手作業の性能計測を開始条件から外し、効果を見込める三群の改善を順に完了した。
upstream の配布版に対応するソースが不明なので、PR と独自配布の判断は保留した。

## History
性能対策の選定に先立って計測案が挙がったが、ユーザーは手作業の計測負担を避けることを求めた。
対策は構造から期待効果を見積もり、次の三群に整理した。

- 第 1 群は、表示範囲を中心とする描画と PDF 解析結果の再利用である。
- 第 2 群は、縮小画像、文字索引、先読みなどの付随処理を遅延させる変更である。
- 第 3 群は、画面外資源の解放と長い文書でのスクロール処理の削減である。

ユーザーは三群をこの順序で実装し、各群の検証まで自動で進める方針を選んだ。
このため、手作業の性能計測は実装の開始条件から外した。

調査では、文書を開くと全ページの描画と PDF の再解析が走る構造が開始時の負荷になっていた。
全ページ分の正しい寸法を持つ枠を維持すれば、画面外ページの描画を遅らせても移動位置を保てると判断した。
そこで、PDF の解析結果を文書単位で再利用する方式を採用した。
描画対象は表示中のページと前後のページに限定した。
実装内容は OpenSpec の `improve-render-performance` とコミット `4ae1356`、`d644615` に記録した。

55 ページの `main.pdf` を使った最初の確認では、PDF Studio で開けていないとの申告があった。
この事象はその後に解消し、原因は特定していない。
その後は拡張機能から開ける状態になり、ユーザーは体感速度の向上を確認した。
この結果を受け、ユーザーは第 2 群と第 3 群も確認待ちで止めずに進めるよう指示した。

縮小画像と文字索引を表示時に一括して作る処理は、画面操作と競合する余地があった。
表示中のページを優先するには、同時描画数を制限し、スクロール方向に応じて先読み順を変える必要があった。
そこで、PDF.js の処理系を画面側から分離した。
縮小画像と文字索引は必要時に作る方式を採用した。
描画要求には表示位置に応じた優先順位を付けた。
実装内容はコミット `dcc3a1b` と OpenSpec の第 2 群に記録した。

長い文書では、描画済みページのキャンバスと PDF.js 側の資源が画面外でも残り続ける問題があった。
現在ページの判定も、スクロールのたびに全ページを調べる方式ではページ数に比例して処理が増える。
そこで、画面外ページの資源を解放し、交差監視で現在ページを追跡する方式を採用した。
検索結果と文字選択を壊さずに資源を再生成できることは、コミット `cfeaefe` と OpenSpec の第 3 群に記録した。

通常版 VS Code で使うため、版を 0.0.8 とした VSIX を作成した。
`main.pdf` は動作確認用のローカル文書なので、`.vscodeignore` に追加して配布物から除外した。
別の VS Code では、導入直後に拡張機能が見えないとの申告があった。
導入先と版を確認した後、ユーザーは拡張機能の表示を確認した。

upstream への反映方法として、次の案を比較した。

- 現在の 13 コミットを一つの PR として送る案。
- 性能改善を目的別の小さな PR に分割する案。
- 独自の VSIX または Marketplace 上の別拡張として配布する案。

upstream の GitHub 上のソースは 0.0.6 相当であり、Marketplace の 0.0.7 に対応するソースを確認できなかった。
現在の差分には性能改善以外の変更も含まれるため、一括 PR はレビュー範囲が広すぎると判断した。
PR を進める場合は、保守者に基準となるソースを確認してから、性能改善だけを分割する案が適切である。
独自配布は可能だが、拡張機能の識別子変更と継続保守が必要になる。
ユーザーはこの時点で upstream への PR と独自配布の判断を保留した。

## Decisions
